# Benchmark methodology

[Back to the README](../README.md)

This page explains **how** the numbers in [`rust-cpu-benchmarks.md`](rust-cpu-benchmarks.md) and
the GPU baselines under `benchmark-results/` are produced, so that anyone on a
different machine can reproduce a comparable snapshot. The methodology and the
specific numbers it produces are deliberately separate: this page is public
durable prose; the JSON/CSV artifacts it describes are gitignored local runs
you generate on your own hardware.

## What is public and what is local

| Artifact | Tracked in git? | Why |
| --- | --- | --- |
| `docs/benchmark-methodology.md` (this file) | Yes | Durable prose about how to measure. |
| `docs/rust-cpu-benchmarks.md` | Yes | One recorded snapshot with methodology and reproduce commands. Treat it as a sample, not a guarantee. |
| `docs/papers/.../results/*.csv`, `*.svg`, `*.json` | Yes (via `.gitignore` allow-lists) | Hash-stable paper evidence; line endings normalized in `.gitattributes` so SHA-256 stays valid across checkouts. |
| `benchmark-results/*.json` | **No** (ignored) | Machine-specific GPU baselines. Regenerable. |
| `relation_graphs_witnesses.jsonl` | **No** (ignored) | Large (~3 MB) research witness data, regenerated by the scripts that produced it. |
| `scripts/results/*` (except the clique baseline fixture) | **No** (ignored) | Generated research runs. |
| `.pytest_cache/`, `.hypothesis/`, `__pycache__/` | **No** (ignored) | Tool state. |

If a snapshot becomes stale on your machine, the right move is to regenerate it
locally, not to edit the checked-in prose.

## CPU backend benchmarks (Python vs Rust)

Entry point: `scripts/benchmark_cpu_backends.py`.

The script:

1. Loads the same `CayleyKernel/_cpu.py` surface twice, once with
   `CAYLEY_KERNEL_CPU_BACKEND=python` and once with `=rust`, so both backends
   share one code path and one set of inputs.
2. Asserts output equality (`twist`, `basis`, `twist_many`, `basis_many`)
   before any timing is taken. If the backends disagree, the run aborts.
3. Auto-tunes per-workload iteration counts with `perf_counter` until each
   workload exceeds ~20 ms, to avoid microsecond-timer noise.
4. Interleaves Python/Rust order each round (round-robin with alternating
   order) and reports **median** per-pair microseconds.

Reproduce the snapshot table:

```sh
python scripts/benchmark_cpu_backends.py \
  --bits 32 64 65 128 129 256 257 1024 4096 \
  --pairs 128 --repeats 5 --dims 1 2 4 8 32 128
```

Reproduce the dense `cpu_multiply` table:

```sh
python scripts/benchmark_cpu_backends.py \
  --bits 8192 16384 65536 262144 1048576 \
  --pairs 16 --repeats 3 --dims 8
```

Native (no Python conversion) Rust benchmark:

```sh
cargo test --manifest-path rust/Cargo.toml --locked --release \
  benchmark_index_paths -- --ignored --nocapture
```

**Caveats the table already spells out**

- The native path uses *sparse* indices; the Python path uses *random* indices.
  Do not compare the two ratios as equivalent workloads.
- The Rust extension uses four-limb hand-rolled sign paths for the two- and
  four-limb ranges; this is not a Rayon or auto-SIMD guarantee.
- No pass/fail threshold is asserted on timings. Correctness is checked
  separately.

## GPU / CUDA baseline

The pytest harness produces the `benchmark-results/*.json` baselines. Use the
same idle GPU and software environment when recording and comparing.

```sh
# Record a fresh baseline at a path that does not exist.
make benchmark-record BENCHMARK_BASELINE=benchmark-results/my-gpu.json

# Compare with the stored baseline using the default 20% slowdown allowance.
make benchmark BENCHMARK_BASELINE=benchmark-results/my-gpu.json
```

Both commands select `tests/test_benchmark.py` with `--run-benchmarks`.
The sampler uses three warmups and five calibrated, synchronized samples.
For sparse versus dense, multi-GPU overlap, and Torch adapter timing,
use `make benchmark-sparse`, `make benchmark-multi-gpu`, and
`make benchmark-torch`. These use the same sampler with alternating
measurement order. See the [testing guide](testing.md#gpu-performance-workloads)
for timing scopes, thresholds, and direct pytest commands.

A new `benchmark-results/<name>.json` is written locally and stays gitignored.
If you want to ship a reference baseline, the right vehicle is a GitHub
Release asset, not the main repo — see `docs/building.md` for the release
workflow.

## Paper evidence (`docs/papers/`)

The CSVs, JSONs, and SVGs under `docs/papers/**/results/` are the one class
of benchmark-adjacent artifact that **is** checked in, because they carry
recorded SHA-256 evidence. Line endings are pinned by `.gitattributes`:

```
docs/papers/physletb-2026-141078/extensions/results/*.csv -text whitespace=cr-at-eol
```

This matters: if you regenerate a CSV on a machine where Git would CRLF -> LF
normalize it, the recorded hashes will no longer match. The `-text` flag plus
`whitespace=cr-at-eol` keeps the bytes the writer emitted. Do not edit the CSV
byte stream by hand after hashing.

## Recommended workflow for a new measurement

1. Write or extend the script under `scripts/` with a stable CLI (seed,
   repeats, pairs, dims as explicit flags).
2. Add a short "Reproduce" section in the corresponding `docs/` page with the
   exact command line.
3. Keep the machine-specific numbers out of git. If a stable snapshot is
   wanted, write it into the doc page once, with the date, hardware, and
   software versions in the same paragraph.
4. For paper evidence, write results to `docs/papers/<paper>/.../results/`
   and record the hashes in the manifest.

That way the public repo holds the *method*, the *one example snapshot*, and
the *reproducible evidence* — while the *current-machine numbers* live in the
checkout that produced them.
